# 서버 PC(매니저) / 클라이언트 PC(공정 담당자) 설정

```
웹(브라우저) ──INSERT──▶ MySQL(command) ◀──0.5초 확인── 매니저 ──Action──▶ 공정 노드(탐색/퍼티/샌딩) ──▶ 로봇
웹 ──rosbridge(ws://서버IP:9090)──▶ /estop ──▶ 매니저 ──move_stop──▶ 로봇      (비상정지는 DB를 거치지 않음)
매니저 ──▶ MySQL(wall / gap / task_log)                                     (DB 쓰기는 매니저만)
```

---

## 공통 (모든 PC)

| 할 일 | 이유 |
|---|---|
| 같은 Wi-Fi(같은 서브넷)에 접속 | ROS2(DDS)는 같은 네트워크 안에서 서로를 자동으로 찾는다 |
| `export ROS_DOMAIN_ID=11` (지금 값, 모든 PC 동일) | 값이 다르면 같은 네트워크여도 서로 안 보인다 |
| `export RMW_IMPLEMENTATION=rmw_fastrtps_cpp` (모든 PC 동일) | DDS 구현이 다르면 통신이 불안정하다 |
| `ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET` 확인 (`LOCALHOST`이면 안 됨) | LOCALHOST면 내 PC 안에서만 보인다 |
| 방화벽 끄기 또는 UDP 허용 (`sudo ufw status`) | DDS 탐색이 UDP 멀티캐스트를 쓴다 |
| `git pull` → `colcon build --packages-select rokey_interfaces rokey1` | `Process.action`이 새로 생겨서 **모든 PC에서 다시 빌드**해야 메시지 형식이 맞는다 |
| 확인: 다른 PC에서 `ros2 action list`에 `/process/...`가 보이는지 | 통신이 되는지 가장 빨리 확인하는 방법 |

> Wi-Fi 공유기가 멀티캐스트를 막으면 PC끼리 서로를 못 찾는다. 이럴 때는 유선이나 핫스팟을 쓰거나, FastDDS discovery server를 설정한다.

### ⚠️ 이전 프로젝트 설정이 남아 있는지 확인 (실제로 겪은 문제)
```bash
grep -n "ROS_DISCOVERY_SERVER\|ROS_SUPER_CLIENT\|ROS_DOMAIN_ID" ~/.bashrc
```
- `ROS_DISCOVERY_SERVER=172.24.0.136:11811`, `ROS_SUPER_CLIENT=TRUE`가 남아 있으면
  노드들이 **그 탐색 서버를 통해서만** 서로를 찾는다. 그 서버가 꺼져 있으면 **같은 PC 안의 노드끼리도 못 찾는다.**
- 증상: 매니저가 `E_NO_SERVER`로 실패하고, `ros2 node list` / `ros2 action list` 결과가 비어 있다.
- 해결: `.bashrc`에서 그 두 줄을 `#`으로 주석 처리한 뒤 새 터미널을 연다.
  급하면 해당 터미널에서 `unset ROS_DISCOVERY_SERVER ROS_SUPER_CLIENT`를 실행한다.
- `ROS_DOMAIN_ID`가 `.bashrc`에 여러 번 있으면 **마지막 줄 값**이 적용된다(지금은 10 다음에 11 → 11).
  모든 PC에서 최종 값이 같아야 한다.

## 서버 PC (매니저)

| #   | 할 일                                                                                                                   | 이유                                                                     |
| --- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 1   | IP 고정 (공유기 DHCP 예약 또는 netplan 설정)                                                                                     | 웹·클라이언트가 이 IP로 DB(3306)와 rosbridge(9090)에 접속한다                         |
| 2   | `sudo apt install mysql-server python3-pymysql ros-jazzy-rosbridge-suite`                                             | MySQL은 DB, pymysql은 매니저의 DB 접속, rosbridge는 웹 비상정지·상태 표시용               |
| 3   | DB 계정 만들기 (아래 SQL)                                                                                                    | 매니저와 백엔드가 같은 계정으로 접속한다. root 계정은 쓰지 않는다                                |
| 4   | 새로 만들 때: `sudo mysql < ~/ws_cobot_pjt/ws_dsr/src/rokey1/db/schema.sql`<br>11/17 첫 버전이 이미 있으면: `mysql -u cobot -pcobot < ~/ws_cobot_pjt/ws_dsr/src/rokey1/db/migrate_01.sql` (한 번만) | 테이블 6개(command, run, wall, gap, task_log, quality)를 만든다. 구조는 이 파일들로만 관리한다 |
| 5   | 백엔드가 다른 PC에 있으면 `/etc/mysql/mysql.conf.d/mysqld.cnf`에서 `bind-address = 0.0.0.0`으로 바꾼 뒤 `sudo systemctl restart mysql` | 기본값(127.0.0.1)에서는 다른 PC가 DB에 접속할 수 없다                                  |
| 6   | `rokey1/config/robot.yaml`의 `db:` 항목 확인 (매니저와 DB가 같은 PC면 `127.0.0.1`)                                                 | 매니저가 이 값으로 DB에 접속한다                                                    |
| 7   | 실행: `ros2 launch ~/ws_cobot_pjt/ws_dsr/src/rokey1/launch/manager.launch.py`                                           | 매니저와 rosbridge를 함께 띄운다. robot_state_publisher는 bringup이 이미 띄우므로 넣지 않았다 |
| 8   | 단독 테스트: 위 명령 뒤에 `fake:=true`를 붙여 실행                                                                                   | 공정 노드가 없어도 가짜 서버로 DB 기록 흐름을 확인할 수 있다                                   |
| 9   | 시연 전 `mysqldump -u cobot -p cobot > backup_$(date +%m%d).sql`                                                         | 시연 중 데이터가 꼬여도 되돌릴 수 있다                                                 |
| 10  | `develop` 브랜치 병합 관리 (하루 1회 이상)                                                                                        | 강사님 요청. 통합 구조는 매니저가 관리한다                                               |

```sql
-- 3번: DB 계정 만들기 (sudo mysql 에서 실행)
CREATE USER 'cobot'@'%' IDENTIFIED BY 'cobot';
GRANT ALL ON cobot.* TO 'cobot'@'%';
FLUSH PRIVILEGES;
```

### 설치 후 단계별 확인 (11/17 서버 PC에서 실제로 해 본 순서)

**① DB 계정·테이블 확인**
```bash
mysql -u cobot -pcobot cobot -e "SHOW TABLES;"
```
정상이면 `command, gap, quality, run, task_log, wall` 6개가 나온다.

| 증상 | 원인 | 해결 |
|---|---|---|
| `ERROR 1049 Unknown database 'cobot'` | schema.sql이 적용되지 않음. 상대경로로 실행했는데 현재 폴더가 달랐던 경우 | **절대경로**로 다시 실행: `sudo mysql < ~/ws_cobot_pjt/ws_dsr/src/rokey1/db/schema.sql` |
| `ERROR 1045 Access denied for user 'cobot'@'localhost'` | 비밀번호를 잘못 입력함. 입력해도 화면에 안 보여서 **한/영이 한글 상태**면 다른 글자가 들어간다 | 영문 상태에서 다시 입력하거나, `-pcobot`처럼 붙여 써서 바로 확인 |
| `-p cobot` 처럼 띄어 씀 | `cobot`은 비밀번호가 아니라 **DB 이름**으로 해석된다 | 비밀번호는 프롬프트에서 입력한다 (정상 동작) |

**② 매니저 + 가짜 공정 서버 실행** (터미널 1)
```bash
ros2 launch ~/ws_cobot_pjt/ws_dsr/src/rokey1/launch/manager.launch.py fake:=true
```
정상 로그:
```
[manager-3] ... [dsr01.manager]: state: IDLE
[rosbridge_websocket-1] ... Rosbridge WebSocket server started on port 9090
```

**③ 웹 대신 START 명령 넣기** (터미널 2)
```bash
mysql -u cobot -pcobot cobot -e "INSERT INTO command (cmd, purpose, material, note) VALUES ('START', 'TEST', 'clay', 'fake test');"
sleep 10
mysql -u cobot -pcobot cobot -e "SELECT * FROM command; SELECT * FROM run;
SELECT log_id,task_code,step,attempt,success,gap_id,contact_ratio,params FROM task_log;"
```
정상 결과 (11/17 실제 결과):
```
cmd_id cmd   status   created_at  →  updated_at
2      START DONE     18:34:01    →  18:34:07     (피드백 6번 × 1초 = 약 6초)

log_id task_code step       success gap_id
2      EXPLORE   explore_a  1       NULL    ← 탐색은 틈이 없으므로 NULL
3      EXPLORE   explore_b  1       NULL
4      PUTTY     putty_a    1       1       ← 탐색 결과가 gap 테이블에 저장되고 그 id가 넘어감
5      PUTTY     putty_b    1       1
6      SANDING   sanding_a  1       1
7      SANDING   sanding_b  1       1
```
| 결과 | 뜻 |
|---|---|
| status가 PENDING에서 안 바뀜 | 매니저가 DB에 접속하지 못함 → robot.yaml `db:` 항목과 MySQL 실행 상태 확인 |
| status FAILED + task_log에 `E_NO_SERVER` | 매니저가 공정 Action 서버를 못 찾음 → 위 "이전 프로젝트 설정" 확인, `fake:=true`로 띄웠는지 확인 |
| status DONE + 위 표처럼 7줄 | 정상 |

**④ 벽·틈 테이블 확인**
```bash
mysql -u cobot -pcobot cobot -e "SELECT * FROM wall; SELECT * FROM gap;"
```

**⑤ 상태 토픽 / 비상정지**
```bash
ros2 topic echo /manager/state                         # IDLE → RUNNING → IDLE
# START를 넣고 2~3초 안에:
ros2 topic pub --once /estop std_msgs/msg/Empty {}
```
매니저 로그에 `state: ESTOP`, task_log에 `ESTOP / estop / success=0` 줄이 생기면 정상이다.
로봇 bringup이 꺼져 있으면 정지 요청(move_stop)은 아무 효과 없이 넘어간다. 실제 로봇에서는 정지가 되는지 꼭 따로 확인한다.

**⑥ 테스트 데이터 정리** (시연 전)
```bash
mysqldump -u cobot -pcobot cobot > ~/backup_$(date +%m%d_%H%M).sql      # 먼저 백업
mysql -u cobot -pcobot cobot -e "SET FOREIGN_KEY_CHECKS=0; TRUNCATE quality; TRUNCATE task_log; TRUNCATE gap; TRUNCATE wall; TRUNCATE run; TRUNCATE command; SET FOREIGN_KEY_CHECKS=1;"
```

## 클라이언트 PC (공정 담당자: 탐색 / 퍼티 / 샌딩)

| # | 할 일 | 이유 |
|---|---|---|
| 1 | 공통 설정 + 빌드 | 매니저와 같은 `Process.action` 형식을 써야 한다 |
| 2 | 내 공정을 **Action 서버**로 만든다. 이름: `/process/explore`, `/process/putty`, `/process/sanding` | 매니저가 이 이름으로 작업을 시킨다 (`rokey_interfaces/action/Process`) |
| 3 | goal에서 받는 값: `start_point`, `end_point` (base 기준 mm), `gap_id`, `run_id` | 틈 좌표는 매니저가 DB에서 꺼내 넘겨준다 |
| 4 | **세부동작 하나가 끝날 때마다 feedback 1번** (step, step_success, error_code, fail_reason, joint, task, force, duration_ms, **params_json, contact_ratio, force_stats_json**) | feedback 1번이 그대로 task_log 1줄이 된다. "무조건 DB에 남기기" 규칙 |
| 4-1 | `params_json`: 그 동작에 **실제로 쓴** 값을 JSON 문자열로 (예: `json.dumps({"target_fz": -10, "vel": 30})`) | YAML 값은 계속 바뀐다. 그때 쓴 값이 있어야 어떤 값이 좋았는지 분석할 수 있다 |
| 4-2 | 힘제어 동작: fz를 주기적으로 리스트에 모아 `utils.force_stats.summarize(fz, target, tol)` → `contact_ratio`, `force_stats_json`에 채움. 힘제어 없는 동작은 비워 둔다 (기본값 -1 → DB에는 NULL) | 접촉 유지 비율이 "벽에서 뜨는 문제"를 숫자로 보여준다. tol은 robot.yaml `force.<키>.tol` |
| 4-3 | 시도 번호(attempt)는 매니저가 넣으므로 신경 쓰지 않아도 된다 | 재시도는 매니저가 관리한다 |
| 5 | step 이름은 `대분류_소분류` (예: `putty_scrape`). robot.yaml의 force 키와 같은 이름으로 | 기록과 파라미터를 같은 이름으로 찾을 수 있다 |
| 6 | 실패하면 result에 `error_code`를 채운다 (`E_GRIP / E_FORCE / E_SINGULAR / E_TIMEOUT / E_NO_GAP`) | 매니저가 이 코드를 보고 재시도·복귀·정지를 결정한다 (manager.py의 `POLICY`) |
| 7 | 탐색 담당: result의 `wall`(12개: top, floor, right, left 순서로 xyz)과 `gaps`(틈 1개당 6개)를 채운다 | 매니저가 이 값을 wall/gap 테이블에 저장한다 |
| 8 | 동작 사이사이에 `goal_handle.is_cancel_requested`를 확인하고, 요청이 있으면 `canceled()` | 매니저가 STOP 명령이나 비상정지 때 goal을 취소한다 |
| 9 | **DB에 직접 쓰지 않는다** (pymysql 설치 불필요) | DB 쓰기를 매니저 한 곳으로 모아야 상태가 꼬이지 않는다 |
| 10 | 파라미터는 `from utils.config import CFG`로 읽는다. 워크스페이스 경로가 다르면 `export ROKEY_CONFIG=<robot.yaml 경로>` | 값을 바꿀 때 코드를 고치지 않고 재시작만 하면 된다 |
| 11 | 노드를 시작할 때 `utils.singularity.apply(DSR_ROBOT2)`를 1회 호출 | 특이점 처리 방식을 모든 공정에서 똑같이 쓴다 |
| 12 | 도구 위치 같은 하드웨어 고정값은 **각자 코드에서** 처리 | 결정 사항. 병합할 때 robot.yaml로 옮길지 검토한다 |
| 13 | 단독 테스트: `ros2 action send_goal /process/putty rokey_interfaces/action/Process "{task_code: PUTTY, run_id: 0, gap_id: -1, start_point: [..], end_point: [..]}" --feedback` | 매니저 없이 내 공정만 확인할 수 있다 |
| 14 | 각자 브랜치에서 작업하고, 동작을 확인한 뒤 `develop`에 push (하루 1회 이상) | 버전 관리 이력으로 진행 상황을 공유한다 |

> 로봇 bringup(`sodreal`)은 **로봇에 연결된 PC 한 대에서만** 실행한다. 두 군데서 띄우면 노드 이름과 서비스가 겹쳐 충돌한다. 다른 PC는 DDS로 그 서비스를 호출하면 된다.

## 웹(프론트·백엔드) 담당

| # | 할 일 | 이유 |
|---|---|---|
| 1 | 시작 버튼 → `INSERT INTO command (cmd, purpose, material, note) VALUES ('START', 'TEST'\|'EXPERIMENT'\|'DEMO', 'putty'\|'clay', '메모')` | 실험 데이터와 시연 데이터를 나중에 걸러낼 수 있다 (run 테이블로 복사됨) |
| 2 | 정지 버튼 → `INSERT INTO command (cmd) VALUES ('STOP')` | 일반 정지는 DB 경로 |
| 3 | 비상정지 버튼 → rosbridge(`ws://서버IP:9090`)로 `/estop` (std_msgs/Empty) 발행 | DB를 거치면 늦다 |
| 4 | 상태 표시 → rosbridge로 `/manager/state` (std_msgs/String) 구독 | IDLE / RUNNING / ERROR / ESTOP |
| 5 | 작업 후 점수 입력 화면: 틈마다 퍼티·샌딩 1~5점 → `INSERT INTO quality (run_id, gap_id, task_code, score, rater, note) VALUES (...) ON DUPLICATE KEY UPDATE score=VALUES(score), note=VALUES(note)` | 성공/실패만으로는 더 좋은 값을 고를 수 없다. 같은 틈을 다시 매기면 덮어쓴다 |
| 6 | 틈 목록: `SELECT g.gap_id FROM gap g JOIN wall w USING (wall_id) WHERE w.run_id = ?` | 점수 입력 화면에 보여줄 틈 |
