# 매니저 통합 구조 설계 (11/17 회의 후속)

## Context
11/17 회의에서 "공정별 단위 기능만 있고, 전체를 관리하는 매니저와 인터페이스가 없다"는 지적을 받았다.
수요일 점심 이후 매니저 초안을 시연해야 한다(DB로 데이터를 관리하는 흐름).
이번 문서는 사용자와 합의한 구조를 바탕으로 **인터페이스·DB·YAML·매니저 뼈대**를 만드는 계획이다.
하드웨어 고정값(도구 위치 등)은 각자 공정 코드에서 처리하고, 병합할 때 반영한다(이번 범위 제외).

## 확정 사항
- 명령 경로: 웹 → 백엔드 → MySQL(`command` 테이블) → 매니저가 **0.5초마다 확인**
- 결과 저장: 공정 노드 → (Action 피드백/결과) → 매니저 → MySQL. **DB에 쓰는 건 매니저만** (pymysql 직접 접속)
- 비상정지: 웹 → **rosbridge WebSocket** → ROS로 바로 전달 → 로봇 정지. DB 기록은 정지 후에 함
- 매니저 ↔ 공정 통신: **Action, 기존 ToolTask는 두고 새 양식(`Process.action`)을 만든다**
- 힘제어 값과 웨이포인트: YAML 공통 양식
- util: `singularity.py`(특이점 관리), `camera_up.py`(z 임계값 아래에서 J6 카메라를 위로 유지)

## 1. 새 Action 양식 — `rokey_interfaces/action/Process.action`
피드백 한 번 = task_log 한 줄이 되도록 맞춰서, 매니저가 받은 값을 그대로 DB에 저장한다(**모든 결과가 DB에 남게 하기 위함**).
```
# Goal
string task_code        # EXPLORE / PUTTY / SANDING
int32  run_id
int32  gap_id           # 탐색은 -1
float64[3] start_point  # base 기준 mm
float64[3] end_point
---
# Result
bool   success
string error_code       # "" | E_GRIP | E_FORCE | E_SINGULAR | E_TIMEOUT | E_NO_GAP
string message
float64[12] wall        # 탐색만: top, floor, right, left 각 xyz
float64[]   gaps        # 탐색만: 틈 1개당 [sx,sy,sz,ex,ey,ez]
---
# Feedback  (세부동작 하나가 끝날 때마다 1회 → task_log 1줄)
string  state           # RUNNING / PAUSED / ERROR
string  step            # 대분류_소분류 (YAML 키와 같은 이름)
bool    step_success
string  fail_reason
float64[6] joint
float64[6] task
float64[6] force
int32   duration_ms
```
- 일시정지/비상정지 시 매니저가 goal을 취소(cancel)한다 → 공정 노드는 취소되면 정지

## 2. 상태값과 오류 처리 규칙 (예시, 담당자와 확정 필요)
상태값: IDLE / RUNNING / PAUSED / DONE / ERROR / ESTOP

| 코드 | 재시도 | 이후 대응 |
|---|---|---|
| E_GRIP | 1 | 그 자리에서 정지하고 사용자 대기 |
| E_FORCE | 1 | 대기 자세로 복귀 |
| E_SINGULAR | util로 회피 1회 | 대기 자세로 복귀 |
| E_TIMEOUT | 0 | 정지하고 사용자 대기 |
| E_NO_GAP | 0 | 해당 틈 건너뜀 |
| E_DB | 3 | `logs/pending.jsonl`에 임시 저장, 다시 연결되면 전송 |
| ESTOP | 0 | 정지하고 해제 명령 대기 |

## 3. DB — `db/schema.sql` (Git으로 관리, 담당자 1명)
- `wall`(wall_id, top/floor/right/left 각 xyz, created_at)
- `gap`(gap_id, wall_id FK, start xyz, end xyz, created_at)
- `task_log`(log_id, run_id, task_code, step, success, gap_id FK NULL, joint JSON, task JSON, fail_reason, started_at, duration_ms, force_val JSON)
- `command`(cmd_id, cmd START/PAUSE/RESUME/STOP/ESTOP_LOG, status PENDING/ACCEPTED/DONE, created_at)
- 식별코드는 AUTO_INCREMENT, 6개씩 묶인 값은 JSON, 시연 전 `mysqldump`로 백업

## 4. YAML — `rokey1/config/robot.yaml`
최상위 키: `common`(vel, acc), `poses`(이름: {type: joint|task, value}), `force`(대분류_소분류: stiffness/target/direction/min_force/wait_sec), `util`(singularity, camera_up.z_threshold)

## 5. 만들 파일 (최소 코드, 구현할 때 minimal-robot 스킬 적용)
- `rokey_interfaces/action/Process.action` + CMakeLists에 등록
- `db/schema.sql`
- `rokey1/config/robot.yaml`
- `rokey1/utils/db.py` — `fetch_command / ack_command / insert_wall / insert_gaps / log_step` (DB 실패 시 jsonl에 임시 저장)
- `rokey1/utils/config.py` — YAML 불러오기
- `rokey1/manager/manager.py` — 명령 확인 → 작업 순서 리스트 `[EXPLORE, PUTTY, SANDING]`를 차례로 Action 호출 → 피드백마다 log_step 실행 → 오류 대응 표 적용
- `rokey1/utils/singularity.py`, `camera_up.py` — 뼈대만 (세부 규칙이 정해진 뒤 구현)
- launch: 매니저 + 공정 노드 + rosbridge (robot_state_publisher는 넣지 않음)

## 아직 정해야 할 세부사항
- 오류 대응 표를 공정별로 확정, 시간 초과 기준(초)
- 틈에 방향(rx,ry,rz)·가로/세로 구분·진행 상태 칸이 필요한가
- force 값은 끝날 때 값 / 최대값 / 평균값 중 무엇을 저장할지
- camera_up: z 임계값, 도구를 잡고 있을 때도 적용할지, J6 회전 방향
- singularity: 두산 `set_singularity_handling` 모드 선택, movej로 빠져나갈 때 쓸 자세
- 비상정지 해제 절차, DB 서버의 IP와 계정

## 검증
1. `colcon build --packages-select rokey_interfaces rokey1` → `ros2 interface show rokey_interfaces/action/Process`
2. `mysql < db/schema.sql` 실행 후 테이블 4개 확인
3. 공정 노드 대신 가짜 Action 서버(피드백 2번 보낸 뒤 성공)로 매니저 실행 → command에 START를 INSERT → task_log에 줄이 쌓이고 command가 DONE으로 바뀌는지 확인
4. rosbridge 실행 후 비상정지 토픽을 발행 → 매니저가 goal을 취소하고 ESTOP을 기록하는지 확인
