explore_server가 하는 일

  1. goal을 받으면 ros2 run rokey1 wall_tap을 실행합니다(confirm:=false, out:=~/wall_scan_data/explore_run<run_id>_*.json).
  2. 끝나면 JSON을 읽어 단계(floor / wall / height / width)마다 피드백을 1번 보냅니다. 각 피드백의 params에는 robot.yaml의 wall_tap 값이 들어갑니다.

07발견한 문제

높음틈 자동 감지가 없습니다

난수 시뮬레이션이던 gap_detection은 삭제했습니다. 지금은 explore.gaps에 틈 좌표를 직접 넣어야 퍼티·샌딩이 실행됩니다. 비어 있으면 ALL 공정은 탐색만 하고 끝납니다.

높음putty_load 값이 비어 있어 ALL 공정이 퍼티 단계에서 멈춥니다

robot.yaml force.putty_load의 값이 null이고 tool_held_confirmed: false입니다. 이 상태에서는 /process/putty_load가 E_FORCE로 거부됩니다. 퍼티 담당이 값을 확정해야 합니다.

중간Tool 이름 불일치: Tool Weight_1 과 Tool Weight

rokey1/move.py와 grip_test.py만 "Tool Weight_1"을 씁니다. 펜던트에 둘 다 등록돼 있지 않으면 set_tool이 실패하고, 등록돼 있으면 힘 센서 보정 무게가 다릅니다. 펜던트에서 확인이 필요해서 고치지 않았습니다.

중간explore_server는 실로봇에서도 y 확인 없이 시작합니다

웹 시작 버튼을 확인 단계로 보고 wall_tap의 confirm을 껐습니다. 웹 bringup(sodvir/sodreal)을 쓰면 서버가 그 모드로 켜져 모드가 맞습니다. 터미널에서 띄운 bringup이면 웹에서 누른 버튼과 mode가 같은지 직접 확인해야 합니다(HMI가 외부 bringup의 mode는 알 수 없음).

해결액션 서버를 탭마다 손으로 켜야 하던 문제 (E_NO_SERVER)

공정 ▶ 시작 때 필요한 /process/* 액션이 없으면 그 서버를 bringup 모드로 켜고 준비될 때까지(최대 30 s) 기다립니다. 정지·비상 정지로 서버가 꺼져도 다시 시작만 누르면 됩니다. bringup이 없으면 시작 버튼이 비활성화됩니다(fake:=true는 예외).

중간src/rokey1_/rokey1 때문에 --packages-select rokey1 빌드가 실패합니다

같은 이름 패키지가 둘이라 colcon이 거부합니다. colcon build --paths src/rokey_interfaces src/rokey1로 빌드하거나, rokey1_를 지우거나 COLCON_IGNORE를 두세요.

낮음ROS_DOMAIN_ID만으로는 격리되지 않습니다

서버 PC 셸에 ROS_DISCOVERY_SERVER가 설정돼 있어 다른 ROS_DOMAIN_ID로 띄운 노드도 같은 그래프에 붙습니다. 시험용 노드를 띄울 때 주의하세요. hmi_server는 시작할 때 끝나지 않은 run을 ABORTED로 마감하므로, 공정 중에 두 번째 hmi_server를 띄우면 안 됩니다.

원인 확정bringup이 수십 초~수 분 걸리던 문제: 원격 discovery server

Waiting for data on 'robot_description' topic 경고가 반복되던 원인입니다. Jazzy의 controller_manager는 robot_description을 토픽으로만 받으므로, 같은 PC 노드끼리 서로 찾는 시간이 그대로 bringup 지연이 됩니다. 이 PC는 Wi-Fi 너머 원격 discovery server(172.24.0.136:11811, RTT 평균 약 150 ms)를 거칩니다. sodvir 기준 robot_description 수신: 11-18 0.8~3.4 s → 11-19 27~216 s (설정은 같음). 로컬 discovery로 실행하니 0.8 s, 경고 0회, dsr_controller2 활성까지 8.3 s. 에뮬레이터·하드웨어 초기화는 매번 2 s 안이라 원인이 아닙니다. 해결: 혼자 하는 가상 시험은 sodvir_local(실행 순서 참고), 팀 연동이 필요할 때만 원격 서버(가능하면 유선).

중간discovery 설정이 다른 노드끼리는 서로 안 보입니다

bringup을 로컬 discovery로 띄우고 다른 터미널에서 기본 설정으로 ros2 run rokey1 pick_tap 등을 실행하면 Waiting for service dsr_controller2/system/set_robot_mode ...만 반복되고 로봇이 움직이지 않습니다. bringup·HMI·액션 서버·작업 노드를 모두 같은 설정으로 띄우세요. 긴 env -u … \ 한 줄은 붙여 넣을 때 잘리기 쉬워(실제로 두 번 발생) 터미널에서 unset/export를 먼저 하는 방법을 권합니다. 확인: tr '\0' '\n' < /proc/<PID>/environ | grep -E 'DISCOVERY|SUPER|RANGE'

참고sodreal에서 같은 경고가 끝없이 반복되면 연결 문제입니다

실로봇(192.168.1.100) 연결이 안 되면 하드웨어 초기화 실패(DRCF connecting ERROR) 뒤 controller_manager가 다시 robot_description 대기로 돌아가 경고가 멈추지 않습니다. 11-19에는 유선 랜 enp2s0이 DOWN이었습니다. 랜 연결 · ping 192.168.1.100 먼저 확인.

해결샌딩 벽 법선을 벽 4점으로 계산합니다

Process goal에 wall[12]를 추가했습니다(rokey_interfaces). process_runner가 그 틈의 벽 4점을 보내고, sanding_server가 utils/wall.py의 (오른쪽−왼쪽)×(위−바닥)으로 법선을 구해 툴 자세를 맞춥니다. 퍼티는 아직 +X 벽 전용이라 같은 함수로 법선이 −X에서 5° 넘게 벗어나면 움직이기 전에 거부합니다. 4점이 없으면 E_NO_WALL로 움직이지 않습니다. 탐색 방향(+x/−y 등)과 벽 기울기가 그대로 반영됩니다.

중간wall_tap이 wall_size의 전역 변수에 의존합니다

configure_direction()이 wall_size 모듈 전역값을 바꿉니다. 한 프로세스에서 두 측정을 같이 돌리면 서로 영향을 줍니다. explore_server는 wall_tap을 별도 프로세스로 실행해서 이 문제를 피합니다.

낮음기존 테스트 실패 5건 (putty 3, flake8, pep257)

test_putty_actions.py가 없는 함수 hmi.tasks.putty_arguments와 putty_load 힘 설정을 기대합니다. 이번 정리 전부터 실패하던 테스트입니다.

해결HMI 파라미터가 범위 검사 없이 들어가던 문제

빈 숫자 칸이 0으로 전송되고, 음수 속도·소수 gap_id·200자 넘는 메모·등록 안 된 도구 번호가 그대로 통과했습니다. 범위·정수·글자 수 검사와 액션 서버 모드 검사를 넣었습니다(웹 페이지 구성 → 파라미터 입력 검사).

좋음DB 쓰기 경로가 하나입니다

hmi_server만 DB에 씁니다. 연결이 끊기면 pending.jsonl에 보관했다가 재전송하고, 서버가 꺼져 끝나지 않은 run은 다음 시작 때 ABORTED로 마감합니다.

웹 페이지에서

  1. 브라우저에서 http://<서버PC IP>:8080을 엽니다. 맨 위 연결 칩이 초록인지 봅니다.
  2. 조작 바에서 sodvir(가상) 또는 sodreal(실제)을 누릅니다. 모드 칩이 bringup 연결됨으로 바뀌고 ▶ 시작이 켜지면 준비된 것입니다. bringup 출력은 로그의 [로봇 bringup] 탭. 처음엔 속도를 30~50%로 낮춥니다.
  3. [공정] 탭 → 탐색 선택 → 목적 TEST, 재료, 메모 입력 → ▶ 시작. 탐색 서버가 없으면 HMI가 먼저 켭니다(액션 서버 켜는 중). wall_tap이 바닥 → 벽 → 높이 → 너비를 잽니다.
  4. 끝나면 로그에 wall_id=… · gap_id=[…]가 찍힙니다. gap_id가 비어 있으면 robot.yaml explore.gaps에 틈 좌표를 넣고 다시 탐색합니다.
  5. [공정] → 퍼티 또는 샌딩 → 틈 번호(gap_id)에 위 번호 입력 → ▶ 시작. 한 틈씩 확인한 뒤 전체 공정을 실행합니다.
  6. 실행 기록(run 목록)에 결과(OK / STOP / E_xxx)와 data_check가 표시됩니다. 문제가 생기면 ■ 정지, 위험하면 비상 정지(Esc) → 원인 해결 후 RESET → ▶ 시작(꺼진 서버는 자동 재시작).

퍼티 단계는 robot.yaml force.putty_load 값이 null이면 E_FORCE로 거부됩니다(퍼티 담당이 값 확정 필요).

막힌 곳 찾는 순서

  1. 웹 실행 기록의 result를 봅니다 → 오류 코드로 어느 공정인지 알 수 있습니다.
  2. DB task_log에서 success=0인 첫 줄 → 단계(step)와 fail_reason.
  3. task_log가 비어 있으면 rqt_graph / ros2 action info로 서버가 떠 있는지 → rqt_console로 그 서버의 Error 로그.
  4. 노드가 Waiting for service …만 반복하면 그 노드와 bringup의 discovery 설정이 같은지 봅니다(/proc/<PID>/environ의 ROS_DISCOVERY_SERVER · ROS_AUTOMATIC_DISCOVERY_RANGE).
  5. 로봇이 안 움직였으면 Topic Monitor의 /dsr01/joint_states·/dsr01/error와 Service Caller의 get_robot_state로 컨트롤러 상태.
